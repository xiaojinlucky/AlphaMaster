# WO-AM-08 在线 SQLite 备份合同修复

时间：2026-07-29 11:00–11:40（Asia/Shanghai）

## 结论

- 第 29 次备份已完成首件 000333 的业务资产收口，但旧脚本把 Web 运行中
  持续变化的 `training_queue_v2.sqlite3-wal` 当成普通文件，导致末尾大小
  复核失败。
- `scripts/backup_am_assets.py` 已改为对 34 个 SQLite 主库逐个执行在线
  `Connection.backup()`，把尚在 WAL 中的已提交事务纳入同一快照；快照随后
  强制转换为自包含的 `journal_mode=DELETE`，并执行 `integrity_check`。
- 远端已有 8 个旧 WAL/SHM 文件。仅发布 DELETE 模式主库仍可能重放旧 WAL；
  独立审查用有效旧 WAL 复现了快照后数据污染。因此每个快照现在同时生成
  0 字节 `-wal`、`-shm`，三个文件全部进入传输清单和 staging 精确集合校验。
- GitHub 发布前的第二轮对抗复核发现：旧实现只是三个文件分别原子替换，
  如果在 sidecar 已清零、主库尚未替换时崩溃，会暂时破坏上一代可恢复备份。
  当前实现已升级为完整版本合同：先以上一完整版本的硬链接副本为基底构造
  新版本，替换本轮文件并闭合目录，最后才原子替换根目录的 `CURRENT` 指针。
  上一完整版本始终保留；失败发生在指针切换前时，恢复入口完全不变。
- 普通源目录中的运行态 WAL/SHM 不再直接传输；SQLite 文件集合若在快照与
  清单阶段之间新增或消失，整轮失败关闭。
- 每轮使用唯一的本地清单目录和远端 staging。tar/SSH 全部成功、staging
  路径和大小精确一致后才构造完整版本；远端库存始终解析 `CURRENT` 所指
  版本。远端 `find`、SSH、tar 任一错误均不再吞掉；备份根、`.incoming`、
  staging、`.generations`、版本目录和 `CURRENT` 均先用 `lstat` 验证原始
  对象身份，再检查解析后的父目录边界。失败清理通过绑定 `.incoming`
  目录描述符的抗符号链接 `rmtree` 执行，不能跨出备份根。
- 切换 `CURRENT` 前，完整版本中的普通文件与全部目录均执行 `fsync`，
  `.building` 改名为正式版本后再同步 `.generations` 父目录；随后写入并
  同步临时指针，原子替换 `CURRENT`，最后同步备份根。异常退出只清理由
  本轮随机版本名精确绑定的 `.building`、未发布正式版本和临时指针；上一
  完整版本及已切换版本不删。清理正式版本前还会读取磁盘 `CURRENT`：
  只要它指向本轮版本，或读取结果不确定，就保守保留，不能依赖进程内标志
  判断提交是否已经落盘。
- 当前脚本 SHA-256：

## 验证

- 仓内定向测试：5 通过、0 失败、2 项 Windows 平台跳过；跳过项是只有
  Linux/开发者模式才能创建的目录符号链接行为，正式脚本的原始对象与
  解析边界由发布前独立源码审查复核。
- WAL 在线快照测试证明快照包含已提交事务，`journal_mode=delete`，
  `integrity_check=ok`，两个 sidecar 均为 0 字节。
- 完整版本测试从含有效非零 WAL/SHM 的旧平铺备份迁移到第一代，再连续发布
  第二代；两代均保持可读，旧平铺资产也未改写。
- 失败注入测试把 staging 路径放到允许顶层之外，发布失败且 `CURRENT`
  字节不变，当前完整版本仍可恢复。
- 中段失败测试在已经创建并填充 `.building` 后制造文件/目录冲突；发布
  失败、`CURRENT` 字节不变且本轮 `.building` 清零，没有遗留大文件。
- 提交边界故障注入在 `CURRENT` 已原子替换、进程内成功标志尚未写入时
  强制中断；退出清理读取磁盘指针并保留当前完整版本，恢复入口仍可读。
