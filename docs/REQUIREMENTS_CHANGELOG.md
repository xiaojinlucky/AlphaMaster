# AlphaMaster — 问题、需求、修改意见与完成记录

## 1. 用户目标

- 安装并长期维护自己的公开 AlphaMaster fork；公开是为了让网页版 GPT 与 BioMNI（BIOMNI）直接读取仓库。
- 在原项目上做轻量二次开发，不做无关的大规模重写。
- 使用 Windows 本机选择/准备数据，通过 Slurm CPU 完成训练并自动取回可验证产物。
- 打通本机与服务器的联通和交互，包括上传、提交、状态、日志、取消、恢复、下载和结果校验。
- 统一 01 模型训练、02 策略回测、03 实时分析的前端视觉。
- 前端采用大字体、舒展排版、清晰边框和一致的侧边栏/卡片/控件。
- 旧 MT5/OKX 数据与未来新增数据能便捷进入训练和回测，而不要求用户手写 manifest。
- 回测能够独立选择测试数据，并严格区分训练集重放、样本外测试和重叠诊断。
- 项目内容、规则、问题、需求、完成状态和验证证据提交到公开 GitHub，供网页版 GPT 与 BioMNI 直接读取并充当规划、调研和工单审查者。
- 当前二次开发延续 `AlphaGPT + StackVM + 固定仓位映射 + 回测奖励` 的核心训练边界，同时向大 A 多标的龙头轮动扩展；优先复用成熟组合持仓与调仓框架，不无依据扩张成通用 Alpha 平台。

## 2. 用户明确修改意见

- 01/02/03 的视觉不一致不可接受；不能通过缩小字体、压缩行高或减少留白迁就其他页面。
- 最快、最有效的界面改善是“字体放大 + 排版舒展”。
- Stitch 设计只是参考，必须查看真实运行页面，不能把预览误称为已应用。
- 原始页面的信息和业务内容不得因视觉统一丢失。
- 不要先配置 TradingView。
- 不要把旧 Parquet 缺少 sidecar 解释为数据本身格式错误。
- 必须用 Git 历史区分原作者功能与 fork 新增合同。
- 前端、数据通道等重要任务完成后要由独立审查线程循环复验。
- AlphaMaster 与其他项目必须完全隔离；不能混在一起分析、提交、打包或执行。
- 解决问题从第一性原理出发；开发用剃刀定律，验收用墨菲定律。
- 复杂任务完成后必须由独立线程按需求、逻辑、边界、代码质量、测试和实际运行六维审查；问题分阻塞项和可选优化，只强制修阻塞项。
- 对不清楚的需求一次只问一个问题，解释选项、例子和推荐理由，逐步确认到约 95% 把握。
- `reward` 是否过度依赖交易结果暂记为研究问题 `R-01`，在因果性、回测/实时一致性和模拟盘证据完成前不贸然修改。

## 3. 已发现的主要问题

### 前端

- Stitch 预览和桌面快捷方式启动的生产页面不是同一入口，导致“修改后没有变化”的误解。
- 01、02、03 曾存在侧边栏缩进、激活背景、字号、行高、卡片边框、Tab 拉伸和图表空白带差异。
- 02 回测评估标签在轮询刷新后会被通用“回测绩效”覆盖。
- 数据卡片曾只显示“已注册”，无法区分旧数据用户登记与新版导出器验证。

### 数据与训练

- `NVDA_M5.parquet` 在 Slurm 模式报缺少 manifest；根因是 fork 新增远程身份合同，不是原始数据必然错误。
- 原作者仓库不要求 sidecar；提交 `c3717be` 才为 Slurm 增加该机制。
- 旧 MT5 数据需要可审计登记，但不得冒充新版导出器验证。
- 旧 OKX 归档与新版下载器来源语义不同；下载器必须过滤未完成 K 线。
- 数据来源 allowlist 曾在本地 loader、Slurm control、Worker、进度和训练包之间分叉。
- 训练过程曾用最小策略 JSON 覆盖完整数据身份。
- checkpoint 曾按品种扁平存放，不能安全区分周期、数据哈希和 run。

### 回测与产物

- 策略与测试数据完全同哈希的旧候选合同只能做训练集重放，阻止正常样本外评估。
- 历史策略缺少数据行数、范围和列合同，不能证明样本外边界。
- Slurm 结果曾未完整绑定 `data_start`、`data_end` 和 `columns`。
- README、新手指南和旧 GPT 交接材料曾保留已经过时的候选状态与重新训练语义。
- 旧安全 ZIP 直接基于 Git 树归档，因历史跟踪的 `training_time_XAUUSD.json` 而包含运行态；该 ZIP 未上传 GitHub，后续包必须显式排除并重新扫描。
- 原 `StackVM._normalize_output()` 的全样本时间统计会让历史时点使用未来数据，导致同一时点的前缀计算与全序列计算不一致。
- `JUMP` 类算子还存在独立因果风险：对整段序列做全局标准化会让未来数据改变历史输出，且旧策略/checkpoint 若未绑定新公式执行合同，可能被错误续用。
- 2026-07-20 用户确认后，已修复并随 `67e81f3` 推送多品种时间交集不足时的未来首报价回填：回退只做 `ffill()`，统一裁掉没有历史报价的共同前段，裁后不足 `MIN_BARS` 失败关闭；独立六维审查 `PASS`。
- `model_core/backtest.py::_turnover_quality()` 将 `tanh` 连续仓位转换为 `int(p)`；绝大多数非满仓值被截成 0，导致 reward 中的交易频率质量失真。
- walk-forward validation 分数在每个训练 step 被反复用于冠军、精英池和搜索方向，因此它属于 selection 反馈；是否存在真正独立、密封且只在策略冻结后访问的最终测试集，仍需代码级审查。
- PnL 与 IC 当前使用的目标收益索引看起来相差一期；在合成价格序列证明唯一执行时点和预测 horizon 前，只登记为待验证问题，不先改代码。

### 项目边界与移交

- 曾错误地把另一个独立项目的实盘目标写入 AlphaMaster 的上下文和网页版 GPT 总控材料。
- 该做法违反项目隔离要求：外部模型会把本机—服务器联通任务误导为无关的跨仓库规划。
- 现行要求是 AlphaMaster 移交只包含本仓库事实、需求、代码、验证和后续工单。
- 基于错误移交提交 `281db3d1` 生成的旧源码包已作废，不得交给外部模型；修正提交后必须重新打包和扫描。

## 9. 2026-07-23 大 A 信号优先路线

### 当前现实约束

- 用户当前没有可用于真实交易的 QMT、PTrade 或目标券商量化账户，因此无法对登录、委托、成交、撤单、持仓和交易日恢复做真实验证。
- QMT/PTrade 接口不再是当前开发主线；在真实券商渠道具备前，不用模拟接口冒充实盘闭环。
- 当前主线是“服务器 Slurm 训练 → 回测 → 普通 A 股虚拟信号 → 飞书机器人推送”；信号优先不等于停止训练与回测，三段必须边跑边贯通。

### 已确认的产品合同

- 账户语义：普通 A 股账户，只做多，不产生融券做空建议。
- 因子仓位小于 `MIN_TRADE_EXPOSURE` 时视为无信号；负因子在空仓时观望，在虚拟持仓时转为离场目标。
- 每根已收盘 K 线只产生一个确定性动作：继续持有/观望、买入、加仓、减仓、离场、止盈或止损。
- 用 SQLite 保存虚拟仓位和信号事件；同一监控项、同一已收盘 K 线在轮询或重启后不得重复生成。
- 止损与止盈按已收盘 K 线的收盘价判断。当前参数沿用 `STOP_LOSS_PCT=-2%`、`TAKE_PROFIT_PCT=+4%`；首次止盈后虚拟仓位减半。
- 调仓门槛为目标虚拟仓位变化至少 10%，避免连续仓位的细小变化产生噪声通知。
- 飞书只推送买入、加仓、减仓、离场、止盈和止损；继续持有/观望只入账、不打扰。
- 飞书遇到网络失败、HTTP 429 或服务端 5xx 时最多尝试三次；最终结果写回事件账本并显示在页面。
- 系统不连接券商、不读取交易账户、不提交订单；价格、虚拟仓位、止损和止盈均是人工执行参考。
- 因为系统不知道用户是否真实执行过历史信号，普通 A 股 T+1、停牌、涨跌停和账户实际可卖数量只能在消息中明确提示，不能伪装成已完成的券商级校验。

### 本阶段工程落点

- 通达信作为页面可选的免费 A 股行情源。
- 通达信返回的收盘时间统一换算为项目 `Bar.ts` 的开盘时间；当前只开放可确定已收盘的 1 分钟至日线，周线/月线暂不暴露。
- Windows 的 PyTorch 固定为 2.8 CPU：本机隔离实测 2.8 可导入并计算，2.12/2.13 均触发 `c10.dll` 的 WinError 1114。
- `strategy_manager/signal_lifecycle.py`：只做多动作决策。
- `web/signal_ledger.py`：虚拟仓位、事件幂等和飞书投递状态。
- `web/realtime_manager.py`：已收盘 K 线触发、动作入账和飞书投递。
- `/api/realtime/signals` 与实时分析页：显示最近可执行交易信号。
- 飞书测试与正式投递只接受官方 `https://open.feishu.cn/open-apis/bot/v2/hook/...` 地址。

## 10. 2026-07-23 服务器训练与大 A 自动流水线纠偏
